Case Study

Mapping a 16-Domain Phishing Cluster Using IDN Homograph Evolution and Social-Engineering Diversification

Timeframe Q2 2026
Role Tier 2 Analyst · IDN & institutional phishing
Attack type IDN homograph + institutional phishing
Outcome 16-domain coordinated takedown filed

One low-confidence parked-domain alert unfolded into a 16-domain cluster on shared infrastructure, with the operator's homograph technique visibly evolving to defeat progressively better detection.

The Alert

A single brand-impersonation alert fired on a parked domain on the .ph ccTLD containing the client bank's trademark verbatim. On its own, a low-confidence hit: the domain served ParkLogic parking-page content, no credential harvesting was observed, and the HTTP 200 response returned generic JavaScript redirect scaffolding.

What kept me from closing it as routine squatting: the .ph TLD specifically targets the Philippine market where the client bank maintains an authorized branch presence. That geographic overlap elevated the consumer-confusion risk beyond generic domain parking.

What I Saw

The initial signal from the first domain: 

=== DNS Resolution ===
Timestamp (UTC): [redacted]
Query: [client-bank]isube.ph → A record
Result: [x.x.x.x]

=== Reverse DNS ===
Query: [x.x.x.x] → PTR
Result: [parking-node].parklogic.com

=== HTTP Request ===
Target: [client-bank]isube.ph
Response Code: 200 OK
Server: Apache/2.4.6 (CentOS) OpenSSL/1.0.2k-fips PHP/5.5.38
Body: JavaScript redirect to /page/bouncy.php with obfuscated
      bpae= parameter (ParkLogic parking monetization script).

A parked domain on ParkLogic infrastructure, hosted on Linode/Akamai. The parking content alone isn't conclusive, ParkLogic legitimately monetizes unused domains. What made me pivot instead of close: the domain wasn't typosquatting or using a generic keyword. It embedded the client bank trademark verbatim and paired it with a .ph ccTLD that maps to a real client operating geography. That combination warranted infrastructure-level investigation, not just content-level triage.

How I Investigated

  1. Pivoted on the IP, not the domain. I ran reverse DNS on the hosting IP and confirmed the PTR record pointed to ParkLogic's Philippine-targeted Kubernetes lander cluster. I chose to pivot on IP rather than domain registrant because ParkLogic parking infrastructure often clusters domains from the same buyer on the same IP block, making the IP a better pivot point for discovering sibling domains than WHOIS alone.
  2. Identified sibling domains through alert-queue correlation and passive DNS. Cross-referencing the IP against the broader alert queue surfaced additional [client-bank]*.ph domains resolving to the same address. Each new domain I found, I resolved DNS for both apex and www subdomain to confirm identical infrastructure. This grew the cluster from 1 to 16 domains across several investigative sessions.
  3. Decoded all Punycode/IDN domains to identify homograph substitutions. Five of the sixteen domains used xn-- Punycode encoding. I decoded each and ran character-by-character Unicode comparison against the legitimate client trademark string. This revealed a deliberate homograph evolution pattern: the operator progressed from naive single-block Latin Extended-A substitutions to advanced cross-script (Greek + Latin) and intra-Latin cross-block (Latin Extended-A + Latin Extended Additional + Latin Extended-B) techniques designed to evade progressively more sophisticated homograph detection filters.
  4. Probed HTTP and TLS on every domain to assess operational readiness. I ran HTTP GET requests and HTTPS probes with TLS certificate inspection against all 16 domains. Results split into three categories: one domain serving live parking content (HTTP 200), the rest returning 503/timeout with origin connection refused, but 13 of 15 non-live domains had active TLS certificates configured (30-day validity, non-wildcard, exact CN match). This confirmed the dormant domains weren't abandoned registrations; they were pre-activation infrastructure with TLS readiness, awaiting deployment.
  5. Classified the institutional domain suffixes by social-engineering intent. Seven domains shared a [client-bank]conflictresolution prefix and diverged only at the suffix: reporting, compliance, reconciliation, litigation, reparation, guidelines, experts. Rather than treating these as duplicates, I mapped each suffix to the psychological pressure it applies: fear (litigation, compliance), hope (reconciliation, reparation), trust (guidelines, experts), duty (reporting). This revealed a professionally designed social-engineering matrix covering the full victim-psychology spectrum, not random domain generation.
  6. Mapped to MITRE ATT&CK and documented the full cluster for coordinated takedown. Final mapping: T1583.001 (Acquire Infrastructure: Domains), T1328 (Buy Domain Name), T1566.002 (Phishing: Spearphishing Link), T1036 (Masquerading), T1056.003 (Input Capture: Web Portal Capture). Compiled the full 16-domain set with per-domain DNS, HTTP, TLS, and obfuscation analysis into a single intelligence package for coordinated abuse filing.

What It Turned Into

Coordinated takedown requests filed against all 16 domains targeting three providers simultaneously: Linode/Akamai (hosting abuse), ParkLogic (parking-infrastructure abuse), and the .ph registry (trademark complaint).

The investigation also produced a reusable Punycode homograph detection methodology, specifically the finding that intra-Latin cross-block substitutions (e.g., Latin Extended-A + Latin Extended Additional) evade the majority of commercial IDN homograph filters that only check for cross-script mixing (Latin vs Greek vs Cyrillic). That detection gap was documented and flagged for integration into monitoring rulesets. One domain in the cluster included a per-victim ?entity=[redacted] tracking parameter, confirming at least one domain was configured for targeted spearphishing rather than broadcast distribution.

What I'd Do Differently

Initial investigation was linear; I fully analyzed each domain before moving to the next, which meant the cluster picture emerged slowly over multiple sessions. On a similar case now, I'd front-load a batch DNS + HTTP sweep of all candidate domains against the pivot IP first to establish cluster scope before deep-diving individual domains.

I'd also automate the Punycode decode-and-compare step. Manually running character-level Unicode comparison across five IDN domains was accurate but slow. A lightweight script that decodes, diffs against the target trademark, and flags the Unicode block of each substituted character would cut the homograph analysis phase from about 15 minutes per domain to under a minute.
