Case Study

Escalating a Trademark Alert into a FERPA Violation and Serial Ban-Evasion Pattern on GitHub

Timeframe Q2 2026
Role Tier 2 Analyst · Brand & platform abuse
Attack type Trademark to FERPA + ban evasion
Outcome Multi-channel GitHub abuse filing

A routine trademark alert on a GitHub repo turned out to be serving scraped student data from a real school district, and the username's "3" told me it wasn't the operator's first account.

The Alert

A brand monitoring alert flagged a GitHub repository using a client LMS platform trademark in both the repository name and username: [client-platform]scraper3/[client-platform]scraper3.github.io. On the surface, a standard trademark case, unauthorized use of the product name in a third-party tool.

What made it non-routine: the repository wasn't just using the brand name. It was a GitHub Pages site actively serving scraped data, and the file listing referenced real school districts and student grade levels by name. That shifted the assessment from trademark triage into something significantly more serious.

What I Saw

The repository file listing on the main branch: 

[client-platform]scraper3/[client-platform]scraper3.github.io
├── 2025-09-14.json
├── all[redacted-district]9thgrade-v1.json
├── all[redacted-district]9thgrade.html
├── data-march-2026-test.html
├── gp-photos-db.txt
├── gp-photos.html
├── index.html
├── onrender-[client-platform]scraper.html
└── [client-platform]-scraper-how-it-started.js

45 commits · main branch · HTML 100% · 0 stars · 0 forks
Username:   [client-platform]scraper3
Hosted via: GitHub Pages (publicly accessible)

Three things escalated this beyond trademark. First, all[redacted-district]9thgrade - the district abbreviation mapped to a real U.S. public school district; 9th graders are 14-15 year old minors. This repository was publicly exposing scraped student data from a real school district. Second, gp-photos-db.txt and gp-photos.html - a photo database and display page, potentially containing images of minors scraped from the platform. Third, the repository description referenced instructions to "keep moving 1 number up if we detect that Security is blocking the current version" - explicit guidance for bypassing the platform's security controls.

How I Investigated

  1. Pivoted on the username suffix, not the repository content. The "3" in [client-platform]scraper3 was the first non-obvious signal. GitHub usernames are unique, so a "3" suffix strongly implies [client-platform]scraper and [client-platform]scraper2 existed previously and were terminated (an inference to be confirmed via GitHub's account-linkage investigation, not an established fact). I flagged this as a serial ban-evasion pattern rather than a first-time violation, which changes the enforcement strategy: GitHub Trust & Safety can investigate linked accounts and implement broader blocks rather than just removing a single repository. This is the difference between whack-a-mole and permanent resolution.
  2. Classified the file names against real-world entities. The district abbreviation in the filename wasn't a generic test string; it mapped to a real U.S. public school district. The -v1 suffix on the JSON file indicated iterative scraping runs. data-march-2026-test.html confirmed the tool was actively maintained as recently as March 2026, so this wasn't an abandoned experiment. I verified the district name to confirm the data referenced real minors, not synthetic test data.
  3. Assessed the photo database for child-safety risk. The gp-photos-db.txt and gp-photos.html files indicated the scraper was collecting not just text data but potentially student photographs. Combined with the 9th-grade targeting, this elevated the case from a data-privacy concern to a child-safety concern, which changes the reporting priority and the response timeline from GitHub.
  4. Identified the security bypass as a circumvention tool. The referenced instruction to increment version numbers to evade security blocking isn't a vulnerability disclosure or legitimate security research; it's an explicit circumvention tutorial. Under GitHub's Acceptable Use Policies, tools designed to bypass platform security controls without authorization are prohibited. This gave the filing a third independent violation category beyond trademark and data privacy.
  5. Mapped the violation layers to separate GitHub reporting channels. A single trademark report goes through GitHub's legal/DMCA queue, which can take days to weeks. By decomposing the case into its constituent violations, I identified three parallel filing paths with different priority levels and response teams, ensuring the fastest possible takedown through the channel most likely to act immediately.
  6. Identified the secondary hosting reference. The file onrender-[client-platform]scraper.html referenced deployment on Render (a cloud hosting platform), indicating the scraping tool itself runs on infrastructure outside GitHub. This meant the GitHub takedown would remove the data display layer but not the scraping engine, requiring a parallel abuse report to Render to fully disrupt the operation.

What It Turned Into

Filed abuse reports through three parallel GitHub channels: trademark infringement (DMCA/trademark form, client platform trademark in repo name and username), child-safety/FERPA violation (Trust & Safety, exposed student data and potential photos of minors from a real U.S. public school district), and security-policy violation (abuse report, circumvention tool with explicit bypass instructions).

Flagged the serial ban-evasion pattern (username suffix "3") for account-level investigation rather than single-repo removal. Recommended a parallel abuse filing to Render for the secondary hosting infrastructure referenced in the repository. The multi-channel filing strategy ensured the child-safety report, which carries the highest priority at GitHub, would trigger immediate review rather than waiting in the standard DMCA queue.

What I'd Do Differently

The initial assessment took longer than it should have because I started with the trademark angle and only discovered the FERPA and child-safety dimensions after examining the file listing in detail. On a similar case now, I'd front-load the file-level content assessment before even evaluating the trademark claim; a repository's file names and commit history reveal the actual threat faster than the brand string in the URL.

The lesson is broader than this case: when a brand monitoring alert fires on a code repository, the trademark violation is usually the least important thing happening. The code, the data, and the commit pattern tell you what the real threat is.

Appendix D · Regulatory Framework

FERPA (Family Educational Rights and Privacy Act)
20 U.S.C. § 1232g; 34 CFR Part 99

  Applies because:
  • Affected institution is a federally funded
    U.S. public educational entity
  • Student records scraped from the client LMS
    constitute "education records" under FERPA
  • Public posting on GitHub Pages = unauthorized
    disclosure to third parties
  • No parental consent obtained for disclosure
  • 9th grade students are minors (14-15 years old)

  FERPA violations can result in:
  • Loss of federal funding for the school district
  • Civil liability for the data handler
  • Enforcement action by the U.S. Department of Education

COPPA (Children's Online Privacy Protection Act)
15 U.S.C. §§ 6501-6506

  Potentially applies if:
  • Any scraped students are under 13 years old
  • Photo database contains images of children under 13
  • Data collected without verifiable parental consent

GitHub Acceptable Use Policies
  Violations:
  • Trademark infringement
  • Active malware / exploit distribution (security bypass)
  • Ban evasion (Terms of Service)
  • Privacy violation (exposing PII without consent)
